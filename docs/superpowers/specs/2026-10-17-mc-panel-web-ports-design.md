# mc-panel: web ports for servers (design spec)

- **Date:** 2026-10-17
- **Status:** design approved, not implemented
- **Author:** Jannes Göbel (with Claude)
- **Builds on:**
  - `2026-10-10-mc-panel-instances-design.md` (instances, mc-router, per-server networks)
  - `2026-10-13-mc-panel-installer-design.md` (Caddy, installer)
  - `2026-10-08-mc-panel-foundation-design.md` (security model)

## 1. Goal

A Minecraft server can publish the web interface of a plugin or mod (BlueMap first; generally one HTTP port inside the container) under **the same name as the server**:
- `https://survival.quafter.io` serves the plugin's web page;
- `survival.quafter.io:25565` is the Minecraft server, through mc-router as today.

An admin turns the web port on in the server's settings. Shortly after, the URL answers with a valid certificate. Turning it off or deleting the server removes the URL.

### 1.1 Decisions

| Question | Decision |
|---|---|
| Who may publish a web port | **Admins only**, with sudo. Publishing makes code that runs in the container reachable from the internet. |
| Who may open the web page | **Everyone with the link** (public). The plugin's own security applies; the UI says so. |
| How many ports | **Exactly one per server**: 1024–65535 except 25565 and 25575; the UI suggests 8100 (BlueMap's default). |
| Routing | **A dedicated web router container `mcpanel-web`** managed by the agent (like `mcpanel-router`). Host Caddy terminates TLS and forwards to it. The agent never edits the host Caddy config at runtime, and the panel never sees the web traffic (approaches B and C in §8 were rejected). |
| Certificates | Let's Encrypt **on demand**, only for names on the allow list (§4.3). No wildcard certificate, no DNS-provider API. |

### 1.2 Non-goals

> **Superseded in part (2026-10-21):** "more than one web port per server" and "path prefixes" are now covered by `2026-10-21-mc-panel-web-port-paths-design.md` (up to 8 routes per server, the root plus `/<path>/`). The other non-goals stay.

- More than one web port per server, path prefixes (`/map/`), or extra subdomains like `map.survival.quafter.io`.
- Access protection in front of the web page (basic auth, panel login).
- Non-HTTP protocols (other TCP or UDP ports).
- Custom domains per server; wildcard certificates via DNS challenge.
- Monitoring or alerting on the web page's availability.
- Installing or configuring BlueMap itself (the plugin installs as today via the plugins area).

## 2. Architecture and data flow

```
Browser ─https─▶ host Caddy (catch-all site, on-demand TLS)
                   │  ask: 127.0.0.1:<ask port>  ──▶ mcpanel-web: "is <host> allowed?"
                   └─▶ 127.0.0.1:<proxy port> ──▶ mcpanel-web ──▶ mcpanel-mc-<id>:<web_port>
                                                   (attached to mcpanel-net-<id>)
Panel ──(desired routes)──▶ agent: PUT /v1/web/routes ──▶ mcpanel-web config + networks
```

Components:

1. **`mcpanel-web`** is a container managed by the agent.
   - Caddy image, pinned by digest like the other images.
   - Runs as a non-root UID (65532) with a read-only rootfs (small tmpfs for Caddy's data/config dirs, owned by that UID with mode 0700, because Caddy creates `/data/caddy` at start), `CapDrop ALL`, `CapAdd NET_BIND_SERVICE` (the image's caddy binary carries that file capability, and the kernel refuses to exec it without it in the bounding set; it only allows ports < 1024 in the container's own netns), `no-new-privileges`, and memory and PIDs limits. It gets no Docker socket.
   - Sits on its own network `mcpanel-web` (labelled, IPv4 only, subnet from the instance network pool or its own fixed /28). It is also attached to the network `mcpanel-net-<id>` of **every server with an active web port, and only those**.
   - Publishes exactly two ports, both on `127.0.0.1` only:
     - the proxy port (default 18100), carrying the web traffic;
     - the ask port (default 18101), which answers certificate permission requests.
   - Its configuration is generated by the agent, written atomically to `<instances_dir>/web/` (root-owned, mounted read-only) and applied without a container restart. Preferred: Caddy's admin API on a Unix socket in a root-only directory under `<instances_dir>/web/`. Fallback: Caddy's config file watch.
   - The container exists only while at least one route exists. With zero routes the agent removes it and its network.
2. **Host Caddy** gets one new managed file from the installer, `/etc/caddy/mc-panel-web.caddy`, imported from the Caddyfile like `mc-panel.caddy`. It contains a **catch-all HTTPS site**:
   - `on_demand` TLS whose `ask` points to `http://127.0.0.1:<ask port>`;
   - `reverse_proxy 127.0.0.1:<proxy port>`;
   - its own access log, `/var/log/caddy/mc-panel-web.log`;
   - a commented `X-Robots-Tag: noindex` header the operator can enable.

   The panel site (`<panel domain>`) is more specific and keeps winning for its own name. The installer does not need to know the base domain: the allow list decides.
3. **The panel** stores an optional `web_port` per server and sends the agent the complete list of active routes `{server id, fqdn, port}`. It computes `fqdn` as `<server name>.<base domain>`. It never proxies or inspects web traffic.
4. **The agent** applies the list. It connects and disconnects `mcpanel-web` to and from server networks (only labelled `mcpanel-net-<id>` networks, only after the egress filter covers them, like the router in §F1), writes the config, enforces the port restriction (§4.2) and reports status per route.

What does not change: Minecraft traffic (mc-router on 25565), the Minecraft container (publishing a web port needs no recreate and no revision bump), and the isolation between servers.

## 3. Panel

### 3.1 Data

A migration adds `web_port INTEGER NULL` to `instances` (`NULL` = off), with a CHECK for 1024–65535 except 25565 and 25575. The value is not part of the instance spec sent to the agent for the container and does not bump `revision`.

### 3.2 API

- `PATCH /servers/{id}` accepts `web_port` (integer or `null`).
  - Changing it requires the **admin role and sudo**. A non-admin sending the field gets `403`.
  - Without a configured base domain, setting a port answers `409 conflict` ("base domain required").
  - Audited as `server.web_port_update` with `old` and `new`.
- `GET /servers` and `GET /servers/{id}` return:
  - `web_url`: `https://<fqdn>` when `web_port` is set and a base domain exists, else absent;
  - `web_status`: `off | pending | active | error`;
  - for admins only: `web_port` and `web_error`, the agent's reason, sanitized like `last_error`.
  - Users with `server.view` see `web_url` and `web_status`, not the port.
- OpenAPI, the generated TS types and the MSW mock are updated as for every endpoint change.

### 3.3 Reconcile

`internal/servers` builds the desired route list on every reconcile pass (every 10 s) and after every change to `web_port`, a server's name, the base domain or a server's deletion. It sends the list with `PUT /v1/web/routes` and stores the per-route status it gets back (in memory, like other agent status).

The list is always complete: a server missing from it means its route is removed. Routes are independent of the server's power state: a stopped server keeps its route, and the web page answers 502 until it runs again.

### 3.4 UI

- **Server settings, section "Web interface"** (admins only):
  - a switch and the port field, prefilled with 8100;
  - the status (off/pending/active/error with the reason) and the URL;
  - a hint: "Public for anyone with the link; the plugin is responsible for its own security. BlueMap: set `accept-download: true` in `plugins/BlueMap/core.conf` and keep the web server enabled on this port."
  - Saving goes through the global sudo dialog.
  - Without a base domain the section explains that one must be set first and links to the settings.
- **Server header and overview:** when `web_status` is `active`, a link "Open web map" (`web_url`, new tab, `rel="noopener noreferrer"`) for everyone who can see the server.
- de and en strings; the design system as in `2026-10-14-mc-panel-ui-redesign-design.md`.

## 4. Agent and `mcpanel-web`

### 4.1 Agent API

`PUT /v1/web/routes` with body `{"routes": [{"id": <int64>, "fqdn": "<string>", "port": <int>}]}`.

Strict validation in `agentapi`, rejecting unknown fields:
- at most 500 routes, unique ids, unique fqdns;
- `id` is a managed instance;
- `fqdn` consists of valid lowercase DNS labels (the `instancespec` rules), at most 253 characters, at least three labels;
- `port` is in 1024–65535 and is not 25565 or 25575.

The reply contains a status per id, `active` or `error` plus a sanitized reason (for example "server network missing", "web router not running").

Applying the list is idempotent and serialised with the instance network mutex:
1. Routes exist but the container is missing: create the `mcpanel-web` network and container. No routes left: remove the container and its network.
2. For each route's server, ensure `mcpanel-net-<id>` exists (the F1 rules: labels, IPv4 only, egress coverage), then connect `mcpanel-web`. Disconnect it from every labelled `mcpanel-net-*` network that is not in the list. Unlabelled or foreign networks and containers are never touched.
3. Generate the Caddy config from a fixed template:
   - the proxy server on `:8080` with one host matcher per route → `reverse_proxy mcpanel-mc-<id>:<port>`; unknown hosts get a static `404`, an unreachable upstream a static `502` page;
   - the ask server on `:8081` returns `200` only when `?domain=` is exactly one of the route fqdns, otherwise `404`.
   - Only validated ids, fqdns and ports go into the config: no user text and no template injection.
4. Apply the config (§2) and update the port restriction (§4.2).

### 4.2 Port restriction

`mcpanel-web` must reach only the published port of each attached server. The agent manages the table `bridge mcpanel_web` (the bridge family sees traffic inside a Docker bridge without relying on `br_netfilter`). `mcpanel-web` gets a fixed address on each attached server network (the last usable host of its /28), so the rules can be written before the connect. For each attached server network:
- allow TCP from that address of `mcpanel-web` to the server network's subnet on `dport <web_port>`. The rule targets the subnet, not the server's IP: the only other member, mc-router, listens on 25565 only, and the server's IP is not known before its container runs;
- drop everything else from that address.

The rules are stateless: replies come from the server's side and are not matched, and a connection from `mcpanel-web` is only possible to the published port. They are rebuilt idempotently on every apply and every tick, like the egress filter: self-repairing, and fail-closed. `mcpanel-web` is never on a server network without its rule: it is disconnected before a rule goes, connected only after the rule exists, and disconnected from every server network when the rules cannot be applied. The egress filter (F1) covers the `mcpanel-web` network like every other managed network.

### 4.3 Certificates

Host Caddy asks `mcpanel-web` before issuing a certificate. Only names an admin published are allowed, so nobody can make the host request certificates for invented subdomains and use up Let's Encrypt limits. Issued certificates are cached by Caddy in `/var/lib/caddy` as today.

### 4.4 Headers

- `mcpanel-web` passes `X-Forwarded-For`, `X-Forwarded-Proto` and `Host` through.
- Panel cookies never reach a plugin: `__Host-sid` is bound to the panel's own host name.
- The panel's CSRF check refuses same-site requests from server subdomains, as today.

## 5. Installer

- **New managed file:** `/etc/caddy/mc-panel-web.caddy` (template under `deploy/caddy/`), plus its import line in the installer's Caddyfile, written and validated like `mc-panel.caddy` (`caddy validate` before reload, restore on failure). A foreign Caddyfile gets a hint, as for the panel site.
- **New `agent.toml` keys:** `web_proxy_port` (default 18100) and `web_ask_port` (default 18101). The installer renders the same values into the Caddy file.
- **Images:** the pinned `mcpanel-web` image digest goes next to the itzg/mc-router digests (`internal/config`).
- **`doctor`:**
  - `web_router`: no routes → ok; otherwise the container is running, publishes only on 127.0.0.1, and the bridge table exists;
  - `web_catchall`: a request with an unknown host name gets no certificate and no 200.
- `update` rewrites the files; `uninstall` removes the file, the import line, the container, its network and the bridge table.
- The host firewall is unchanged: 80 and 443 are already open.

## 6. Error handling

| Case | Behaviour |
|---|---|
| The plugin does not listen on the port | `mcpanel-web` answers `502` with a short static page. `web_status` stays `active` (the route is fine). The UI hint names the usual causes. |
| Server stopped | Same as above. It works again after the start, with no action needed. |
| Certificate fails (DNS, rate limit) | Visible only in Caddy's log. `doctor` and the docs point to `journalctl -u caddy` and the wildcard DNS record. |
| Agent unavailable | `web_status = error` ("agent unavailable"). Existing routes keep working, because `mcpanel-web` runs independently. |
| Server deleted / renamed / base domain changed | The next reconcile sends the new list. Old names leave the allow list and get no new certificates. |
| Config apply fails | The agent keeps the last good config. Affected routes report `error`. Nothing is half-applied: the networks and rules match the last good config. |
| Instance network missing | The route reports `error`. The F1 repair (`ensureInstanceNetwork` on start) recreates the network, and the next apply connects it. |

## 7. Testing

- **Go, agent:**
  - request validation (fqdn rules, ports, duplicates, limits, unknown fields);
  - the generated Caddy config (golden test; no injection through fqdns);
  - network connect/disconnect with the Docker mock, including foreign or unlabelled networks left untouched;
  - create and remove at zero routes;
  - the bridge port rules (nftables integration test as root in CI);
  - fail-closed ordering.
- **Go, panel:**
  - only admin plus sudo may change `web_port` (`403` otherwise);
  - audit;
  - `409` without a base domain;
  - reconcile builds the complete list (rename, delete, base domain change);
  - status mapping;
  - viewers do not see the port.
- **Web:**
  - Vitest for the settings section (admin only, sudo, hint, no base domain) and the header link;
  - a mock e2e test: publish, link visible, unpublish.
- **CI acceptance:** a new shard `web` in `scripts/ci-instances/`.
  - A Paper server runs a minimal HTTP responder inside its container (no BlueMap download).
  - Requests with `Host: <name>.<base>` through host Caddy (`tls internal`, using `--resolve`) answer 200 with the responder's body.
  - An unknown host gets no certificate.
  - A second server cannot reach the first one's web port.
  - `mcpanel-web` cannot reach a non-published port of the server.
  - Unpublishing removes the route; zero routes remove the container.
- **Installer:** Bash tests for the new Caddy file (render, validate, restore), the import line, the `doctor` checks and `uninstall`.

## 8. Rejected approaches

- **B. The agent writes host Caddy files with container IPs and reloads Caddy.** The root agent would need write access to `/etc/caddy` and the Caddy admin API, which weakens its sandbox. Container IPs change on recreate, and a broken file could block reloads of the panel site.
- **C. The panel proxies the web traffic.** Untrusted plugin traffic would run through the process that holds sessions and the database: more attack surface and load in the wrong place.
