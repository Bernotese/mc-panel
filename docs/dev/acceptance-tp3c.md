# Abnahme Teilprojekt 3c (manuell, Test-VM)

Spec: `docs/superpowers/specs/2026-10-12-mc-panel-plugins-design.md` (§10).

Automatisch geprüft (CI): Unit-Tests der Upstream-Clients mit echten, gekürzten Antworten (Modrinth, Hangar, Host-Allowlist inkl. Weiterleitungen, Größen- und `Content-Length`-Prüfung, Caches, Dateinamen-Fallback), Auflösen (Tiefe, Paketlimit, Zyklen, extern, inkompatibel, Client-only-Mods), Dateidienst (`/v1/jars` mit Prüfsummen, Cache und Metadaten, Symlinks/FIFOs/Ordner ausgelassen, Upload mit falscher Prüfsumme ohne Rückstände), panel-Tests (Rechte, CSRF, Inventar-Zuordnung, Jobs, `file_exists`, Updates, Rate-Limit, Icon-Proxy, Audit), Vertrag (OpenAPI ↔ Routen, Fehlercodes, Mock pro Operation), Vitest und Playwright gegen den Mock (suchen → installieren mit Abhängigkeit → deaktivieren → Update → entfernen) und die Instanz-Abnahme (`scripts/ci-instances.sh`: panel im Produktionsmodus mit TOTP-Login, Chunky von Modrinth und ViaBackwards samt ViaVersion von Hangar auf einem echten Paper-Server installiert, nach dem Neustart per RCON `plugins` geladen, deaktiviert nicht geladen, Prüfsummen im Dateidienst, Icon-Proxy, Audit).

Manuell auf der Test-VM: alles mit Browser, Minecraft-Client und echter Session.

## Vorbereitung

1. Deploy von `main`: `make deploy-testvm` (alle TP3c-PRs gemerged). Panel: <https://panel.192-168-1-117.sslip.io/>. Logs nebenher: `ssh claude@192.168.1.117 journalctl -u mcpanel-agent -u mcpanel-files -u mcpanel-panel -f`.
2. Ausgehende Verbindungen des panels prüfen: `ssh claude@192.168.1.117 'for h in api.modrinth.com cdn.modrinth.com hangar.papermc.io hangarcdn.papermc.io; do sudo -u mcpanel curl -sS -o /dev/null -w "$h %{http_code}\n" -A "mc-panel/acceptance (https://github.com/Bernotese/mc-panel)" "https://$h/"; done'` → vier Antworten mit HTTP-Status (kein `000`).
3. Als `admin` anmelden. Server `survival` (Paper, aktuelle Version) existiert und läuft. Neuen Server `modded` anlegen: Typ Fabric, Spielversion `1.21.11`, 2048 MiB, starten (der erste Start legt `mods/` nicht unbedingt an – das panel legt den Ordner bei der ersten Installation an).
4. Benutzer `freund` hat nur `server.view` auf `survival` (aus TP3a). Benutzer `helfer` bekommt auf `survival` und `modded` zusätzlich `server.plugins` und `server.power` (Benutzer → Rechte; beim Anhaken von „Plugins/Mods“ erscheint der Hinweis „„Plugins/Mods“ erlaubt Code-Ausführung im Minecraft-Server. Vergib es nur an Personen, denen du voll vertraust.“).
5. Auf dem Mac vorbereiten: eine ältere LuckPerms-Version für Bukkit/Paper von <https://modrinth.com/plugin/luckperms/versions> herunterladen (z. B. `LuckPerms-Bukkit-5.5.53.jar`, Filter Loader Paper und die Spielversion von `survival`).
6. Minecraft Java Edition im selben Netz, Adressen `survival.mc.192-168-1-117.sslip.io` und `modded.mc.192-168-1-117.sslip.io`.

## mrpack-Import (Issue #78)

Spec: `docs/superpowers/specs/2026-10-14-mc-panel-mrpack-import-design.md`. Automatisch geprüft (CI): Index-Validierung inkl. Pfad-Angriffe, Klassifizierung (alle `action`/`reason`), Import-Job (install, update, deaktiviertes Jar, fehlgeschlagener Schritt, `exclude`, `accept_mismatch`), Vertrag, und in `scripts/ci-instances.sh` ein Fabric-Server mit Fabric API (`install`), Sodium (`skip client_only`) und einem unbekannten Hash (`skip not_on_modrinth`) gegen das echte Modrinth.

Vorbereitung: auf dem Mac in der Modrinth-App (oder im Launcher) eine Fabric-Instanz für die Spielversion von `modded` mit Fabric API, Lithium, Sodium und Mod Menu anlegen und als `.mrpack` exportieren; dazu ein eigenes Jar ohne Modrinth-Eintrag in die Instanz legen und beim Export mitnehmen. Auf `modded` vorher eine ältere Lithium-Version im Tab „Dateien“ nach `mods/` hochladen.

| # | Kriterium | Vorgehen | Erwartet |
|---|---|---|---|
| M1 | Vorschau | als `helfer` Server `modded` → Tab „Mods“ → „Modpack importieren (.mrpack)“ → die Datei wählen | Diff: Fabric API unter *Neu* (oder *Unverändert*, falls aus Kriterium 3 vorhanden), Lithium unter *Aktualisiert* (alt → neu), Sodium und Mod Menu unter *Übersprungen* („nur Client“), das eigene Jar unter *Übersprungen* („nicht auf Modrinth – bitte manuell hochladen“), vorhandene Mods außerhalb des Packs unter *Bleibt installiert*, Hinweis auf ignorierte Dateien außerhalb von `mods/`; im Netzwerk-Tab geht nur `modrinth.index.json` hoch (Request < 1 MiB), nicht die ganze Datei |
| M2 | Import | „Importieren“ | Fortschritt pro Jar, danach die neuen Jars in `mods/`, die alte Lithium-Version ist weg, Banner „Neustart nötig“; nach dem Neustart startet der Server (Konsole ohne Mod-Fehler) |
| M3 | Optionale Mods | ein Pack mit einem Eintrag `env.server: optional` importieren und diesen abwählen | der abgewählte Mod wird nicht installiert, die anderen schon |
| M4 | Versionsabweichung | ein Pack für eine andere Minecraft-Version wählen | Warnbox mit Pack- und Server-Version; als `admin` „Server-Version auf X umstellen“ (Sudo-Dialog), danach neue Vorschau ohne Warnung; als `helfer` nur „Trotzdem importieren“, ohne Häkchen ist der Import gesperrt (`409 mrpack_version_mismatch`) |
| M5 | Falscher Loader | ein NeoForge-Pack auf `modded` wählen; ein beliebiges Pack auf `survival` (Paper) | `409 mrpack_incompatible` mit verständlicher Meldung; auf `survival` gibt es den Knopf nicht |
| M6 | Audit | als `admin` Audit-Log, Filter `plugin.` | je Jar `plugin.install` bzw. `plugin.update` mit `via: mrpack`, dazu ein Eintrag `plugin.mrpack_import` mit Pack-Name, Version und Zählern |

Zusätzlich auf dem Handy (oder DevTools-Gerätemodus, 390 px): Installiert-Liste als Karten, Suche und Installieren-Dialog bedienbar, Job-Fortschritt sichtbar, kein horizontales Scrollen der Seite.

Befunde als GitHub-Issue anlegen (`gh issue create`), mit Schritten zum Nachstellen.
