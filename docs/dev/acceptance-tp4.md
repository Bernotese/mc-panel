# Abnahme Teilprojekt 4 (manuell, Test-VM)

Spec: `docs/superpowers/specs/2026-10-12-mc-panel-backups-design.md` (§9).

Automatisch geprüft (CI):
- **Dateidienst:** tar über `os.Root` (Symlinks, Sonderdateien, verborgene Einträge, Schwärzung, Symlink-Tausch während des Durchlaufs, Grenzen), tar-Entpacken mit den Zip-Regeln (Pfad-Tricks, Link- und Geräte-Einträge, doppelte Namen, falsche Größen), Tausch der obersten Ebene, Abbrechen, tar→Zip, Jobs (einer pro Instanz über alle Arten) und echtes restic (init, backup, list, pin, forget mit Policy und Zeitzone, dump, restore, purge).
- **panel:** Zeitplan-Rechnung mit Fake-Clock (Sommerzeit, verpasste Termine, Zeitzonenwechsel), Warteschlange, `save-on` nach jedem Fehler und nach einem Absturz, Restore-Sperre gegen Power und Abgleich, Rechte inklusive Sudo, Audit, `backup.failed` mit Drosselung, `purge_backups`.
- **Vertrag:** OpenAPI ↔ Routen, Fehlercodes, ein Mock pro Operation.
- **Frontend:** Vitest und Playwright gegen den Mock (`web/e2e/backups.spec.ts`).
- **Instanz-Abnahme** (`scripts/ci-instances.sh`) auf einem echten Paper-Server: manuelles Backup mit `save-off`/`save-on` im Log, Repo und tar-Inhalt, Restore mit Sudo, Zip-Download, ein Zeitplan, der in der Zeitzone des panels auslöst, Pin, Löschen, Server löschen mit Purge, Audit.

Manuell auf der Test-VM: alles mit Browser, Minecraft-Client, echter Session, Benachrichtigungen und gestörtem Betrieb.

## Vorbereitung

1. Deploy von `main`: `make deploy-testvm` (alle TP4-PRs gemerged). Panel: <https://panel.192-168-1-117.sslip.io/>. Logs nebenher: `ssh claude@192.168.1.117 journalctl -u mcpanel-agent -u mcpanel-files -u mcpanel-panel -f`.
2. Host prüfen: `ssh claude@192.168.1.117 '/usr/local/bin/restic version; sudo stat -c "%U:%G %a %n" /srv/mc-panel/backups; systemctl show mcpanel-files -p ReadWritePaths -p MemoryMax -p TasksMax -p IOWeight -p CPUWeight -p RestrictAddressFamilies'` → `restic 0.19.1 …`, `mcpanel-mc:mcpanel-mc 700 /srv/mc-panel/backups`, beide Pfade in `ReadWritePaths`, `MemoryMax=1073741824`, `TasksMax=512`, `IOWeight=50`, `CPUWeight=50`, `RestrictAddressFamilies=AF_UNIX`. Außerdem `ssh claude@192.168.1.117 'dpkg-query -W -f="\${Status}\n" tzdata; ls /usr/share/zoneinfo/Europe/Berlin /usr/share/zoneinfo/UTC'` → `install ok installed` und beide Dateien vorhanden (restic liest die Zone von dort und rechnet ohne sie still in UTC).
3. Als `admin` anmelden. Server `survival` (Paper, aktuelle Version) läuft; im Minecraft-Client verbinden (`survival.mc.192-168-1-117.sslip.io`) und neben dem Spawn einen Turm aus **Holz** bauen.
4. Benutzer `freund` hat nur `server.view` auf `survival` (aus TP3a). Benutzer `helfer` bekommt auf `survival` zusätzlich `server.backups` und `server.power` (Benutzer → „Rechte“). Beim Anhaken von „Backups“ erscheint der Hinweis „„Backups“ erlaubt, alle Dateien des Servers herunterzuladen (auch Konfigurationen mit Passwörtern) und den Server auf einen älteren Stand zurückzusetzen. …“.
5. Security Center → „Benachrichtigungen“ → „Benachrichtigung hinzufügen“: Dienst „ntfy“, „Server-URL“ `https://ntfy.sh`, „Topic“ ein zufälliges Thema (im Browser oder in der ntfy-App abonnieren); „Test senden“ kommt an.
6. Einstellungen → „Zeitzone für Backups“ steht auf `Europe/Berlin`.

## Kriterien

| # | Kriterium (Spec §9) | Vorgehen | Erwartet |
|---|---|---|---|
| 1 | Manuelles Backup bei laufendem Server | als `helfer` Server `survival` → Tab „Backups“ → „Backup erstellen“, „Notiz (optional)“ „Holzturm“ → „Backup starten“; parallel Tab „Konsole“ | die Job-Anzeige „Backup läuft …“ zeigt die Schritte „Speichern im Spiel wird angehalten …“, „Daten werden gesichert …“, „Speichern im Spiel läuft wieder …“; die Konsole zeigt `[Rcon: Automatic saving is now disabled]`, `[Rcon: Saved the game]`, `[Rcon: Automatic saving is now enabled]`; danach „Backup abgeschlossen“ und der Snapshot steht als „Manuell“ mit Notiz „Holzturm“, Zeitpunkt und Größe in der Liste; Spieler bleiben verbunden |
| 2a | Zeitplan feuert | Karte „Zeitplan“: „Täglich“, „Uhrzeit“ = jetzt + 3 min, „Letzte behalten“ 2, „Tage behalten“/„Wochen behalten“/„Monate behalten“ 0 → „Zeitplan speichern“ | „Nächster Lauf: …“ zeigt die Uhrzeit, darunter „Uhrzeiten gelten in der Zeitzone des Panels: Europe/Berlin. …“; zur Uhrzeit (± 1 min) startet ein Job („Geplanter Lauf“), danach steht ein Snapshot „Geplant“ da, „Letzter geplanter Lauf: … – erfolgreich“, „Nächster Lauf“ ist morgen |
| 2b | Retention und Anpinnen | den ersten geplanten Snapshot „Anpinnen“; danach den Zeitplan dreimal hintereinander auf jetzt + 2 min stellen und jeden Lauf abwarten | nach dem Anpinnen „Snapshot angepinnt.“, Badge „Angepinnt“ und eine neue Kurz-ID; am Ende: der angepinnte plus die zwei neuesten geplanten Snapshots, ein älterer geplanter ist verschwunden; „Manuell“- und „Vor Restore“-Snapshots unverändert |
| 2c | Zeitzone | als `admin` Einstellungen → „Zeitzone für Backups“ `UTC` → „Zeitzone speichern“; Tab „Backups“ nach ≤ 1 min neu laden (das panel rechnet die Termine beim nächsten Minuten-Tick neu); danach wieder `Europe/Berlin` | „Nächster Lauf“ verschiebt sich um den Abstand zwischen UTC und Berlin (1 bzw. 2 h); der Hinweis nennt die neue Zone; nach dem Zurückstellen stimmt der Termin wieder |
| 3a | Restore | im Spiel den Holzturm durch **Stein** ersetzen; als `helfer` am Snapshot „Holzturm“ → „Wiederherstellen“ → Dialog: „Zum Bestätigen den Namen „survival“ eintippen“ → „Wiederherstellen“ → Sudo (Passwort bzw. TOTP) | der Dialog erklärt Stopp, Sicherheits-Snapshot „Vor Restore“ und Neustart; die Job-Anzeige „Wiederherstellung läuft …“ zeigt „Server wird gestoppt …“, „Sicherheits-Snapshot wird erstellt …“, „Snapshot wird eingespielt …“; währenddessen ist „Starten“ gesperrt („Gerade wird ein Archiv entpackt oder ein Backup wiederhergestellt – Starten ist erst danach möglich.“); Spieler werden getrennt; danach läuft der Server wieder, im Spiel steht der **Holz**turm; in der Liste steht ein neuer Snapshot „Vor Restore“ |
| 3b | Restore umkehrbar | den Snapshot „Vor Restore“ wiederherstellen | im Spiel steht wieder der **Stein**turm |
| 3c | Verborgenes bleibt, gestoppter Server bleibt gestoppt | `ssh claude@192.168.1.117 'sudo ls -la /srv/mc-panel/instances/<id>/ \| grep -E "\.rcon-cli\|\.mcpanel-"'` vor und nach einem Restore; Server stoppen, Restore, Status ansehen | `.rcon-cli.*` vorhanden und nicht aus dem Snapshot überschrieben; ein gestoppter Server ist nach dem Restore weiterhin gestoppt |
| 4 | Download | am Snapshot „Als Zip herunterladen“ | Datei `survival-<JJJJMMTT-HHMMSS>.zip` (Zeitpunkt des Snapshots in der Zeitzone des panels); öffnet im Finder; enthält `world/`, `plugins/`, `server.properties` mit `rcon.password=********`; keine Datei `.rcon-cli.*` |
| 5 | Symlinks | `ssh claude@192.168.1.117 'sudo -u mcpanel-mc ln -s ../<id-eines-anderen-servers> /srv/mc-panel/instances/<id>/fremd'`; Backup erstellen, herunterladen, dann diesen Snapshot wiederherstellen | das Zip enthält keinen Eintrag `fremd` und keine Dateien des anderen Servers; nach dem Restore ist `fremd` weg; die Daten des anderen Servers sind unverändert (`ls -la`, Zeitstempel) |
| 6 | Fehler-Benachrichtigung | `ssh claude@192.168.1.117 'sudo mv /usr/local/bin/restic /usr/local/bin/restic.off'`; Zeitplan auf jetzt + 2 min; Lauf abwarten; Zeitplan erneut auf jetzt + 2 min, Lauf abwarten; dann `sudo mv /usr/local/bin/restic.off /usr/local/bin/restic`, Zeitplan auf jetzt + 2 min | erster Lauf: „Letzter geplanter Lauf: … – fehlgeschlagen“ mit Fehlertext ohne Host-Pfad, eine ntfy-Nachricht „Backup failed: survival“; zweiter Fehlschlag: keine zweite Nachricht (höchstens eine in 6 h pro Server); dritter Lauf erfolgreich, Status wieder „erfolgreich“ |
| 7 | Ohne restic | `ssh claude@192.168.1.117 'sudo mv /usr/local/bin/restic /usr/local/bin/restic.off && sudo systemctl restart mcpanel-files'`; Tab „Backups“ und Tab „Dateien“ öffnen; danach `sudo mv /usr/local/bin/restic.off /usr/local/bin/restic && sudo systemctl restart mcpanel-files` | Tab „Backups“ zeigt nur den Hinweis „Backups sind auf diesem Host nicht verfügbar (restic fehlt oder der Dateidienst ist nicht erreichbar).“, ohne Aktionen; der Dateibrowser funktioniert normal; nach dem Zurückstellen ist alles wieder da |
| 8 | Absturz des panels während eines Backups | `ssh claude@192.168.1.117 'sudo -u mcpanel-mc dd if=/dev/urandom of=/srv/mc-panel/instances/<id>/gross.bin bs=1M count=3072'` (macht das Backup langsam); Backup erstellen; während „Daten werden gesichert …“: `ssh claude@192.168.1.117 'sudo systemctl kill -s KILL mcpanel-panel'`; nach dem automatischen Neustart des panels in der Konsole `save-on` | systemd startet das panel neu; die Konsole antwortet auf `save-on` mit `Saving is already turned on` (das panel hat beim Start den Backup-Job im Dateidienst abgebrochen und `save-on` gesendet); kein laufender Job mehr, „Backup erstellen“ geht wieder; danach `gross.bin` im Tab „Dateien“ löschen |
| 9a | Server löschen mit Backups | neuen Paper-Server `wegwerf` anlegen und starten, Backup erstellen; als `admin` → Server löschen mit „Backups ebenfalls löschen“ | „Server und Backups werden gelöscht …“; `ssh claude@192.168.1.117 'sudo ls /srv/mc-panel/backups/repos /srv/mc-panel/backups/keys'` enthält die ID von `wegwerf` nicht mehr; Audit `server.delete` mit `backups_purged: true` |
| 9b | Server löschen ohne Backups | dasselbe mit `wegwerf2`, ohne die Checkbox | der Dialog weist darauf hin: „Ohne diese Option bleiben die Backups des Servers auf dem Host liegen und belegen weiter Platz.“; Repo und Schlüssel der ID bleiben liegen; Audit `server.delete` ohne `backups_purged` |
| 10a | nur `server.view` | als `freund` Server `survival` öffnen | kein Tab „Backups“ |
| 10b | API-Sperre | als `freund` in den DevTools: `await fetch('/api/servers/<id>/backups').then(r => r.status)` | `403` |
| 11 | Audit | als `admin` Audit-Log, Filter auf `backup.`; danach `ssh claude@192.168.1.117 "sudo -u mcpanel panel audit verify -config /etc/mc-panel/panel.toml"` | `backup.create` (mit Notiz), `backup.restore`, `backup.download`, `backup.pin`, `backup.schedule_update`, `backup.delete` mit Ziel `server:<id>` und Benutzer `helfer` bzw. `admin`; geplante Läufe erscheinen nicht; die Zeitzonen-Änderung steht in `server.settings_update` (`backup_timezone` alt/neu); `verify` meldet OK |
| 12a | Gleichzeitigkeit | zwei Browser-Tabs: in Tab 1 „Backup erstellen“, sofort in Tab 2 „Wiederherstellen“ bzw. „Backup erstellen“ | Tab 2 meldet „Für diesen Server läuft oder wartet bereits ein Backup-Auftrag.“ (`409 backup_running`); keine zweite Job-Anzeige |
| 12b | Entpacken während eines Backups | Server stoppen, ein Backup starten (mit `gross.bin` aus Zeile 8 dauert es lange genug) und währenddessen im Tab „Dateien“ ein Zip entpacken | der Dateidienst lehnt ab (`429 busy`, Meldung „Es läuft bereits ein Entpack-Vorgang.“); nach dem Backup geht das Entpacken |
| 13 | Platte voll beim Restore | `ssh claude@192.168.1.117 'df -B1 --output=avail /srv/mc-panel'`; eine Datei anlegen, die bis auf ~1 GiB alles belegt (`sudo fallocate -l <avail-1G> /srv/mc-panel/fill`); Restore eines Snapshots > 1 GiB starten; danach `sudo rm /srv/mc-panel/fill` | „Wiederherstellung fehlgeschlagen“ mit „Auf dem Host ist nicht genug Platz frei.“ (je nach Füllstand schon beim Sicherheits-Snapshot, weil der Dienst `reserve_bytes` = 2 GiB frei hält); die Server-Daten sind unverändert, der Server startet wieder; nach dem Löschen von `fill` geht der Restore |
