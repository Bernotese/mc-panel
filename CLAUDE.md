# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

mc-panel is a self-hosted Minecraft server panel: a Go backend with an embedded React SPA, released as static `linux/amd64` and `linux/arm64` binaries. Development happens locally on macOS (Apple Silicon); production is an Ubuntu 26.04 LTS VPS set up by the installer (`install.sh`, sub-project 6: panel, agent and the files service as systemd services behind Caddy). Project docs are written in English (keep new docs and spec updates in English):

- `README.md`: what mc-panel is, features, security model, requirements, quickstart. No build steps (those belong in `docs/dev/README.md`).
- `docs/install.md`: operator guide: requirements, DNS, firewall, all `install.sh` options, first admin, update, rollback, doctor, uninstall, backups of keys, troubleshooting. Update it when installer options or paths change.

A feature with manual checks adds them to its area there; there are no per-sub-project checklists.

## Working rules

- **Checks on the Mac:** only `make check` (gofmt, `go vet` for macOS and for Linux incl. the root-only integration test files, `go build` for Linux, TypeScript types, `bash -n` over the installer; ~10 s). Never run `make test`, `make test-race`, `make lint`, Playwright or `make release` on the Mac: the Mac stays clean.
- **Tests on the test VM before every push:** `make test-vm [SUITE=all|go|lint|web|e2e]` copies the working tree (tracked and new files, no push needed) to its own directory on the test VM and runs the suites there as an ordinary user (race tests, golangci-lint + eslint + tsc, Vitest, Playwright against the mock and the real dev backend; the deployed panel is untouched). Run at least the suites your change touches; `all` before a PR is marked ready. SSH to the VM needs the Bash sandbox disabled. The root-only acceptance (nftables, Docker, instances) runs only in CI.
- **CI is the gate before merging:** a pull request runs only the jobs its changed files need (job `changes`); the weekly run runs everything, pushes to `main` everything except the three root jobs (`nftables`, `instances`, `installer`). Jobs without root run on four self-hosted runners on the test VM (label `mcpanel-vm`, no GitHub minutes; their test steps share the `make test-vm` lock), the root jobs on GitHub-hosted runners (details in `docs/dev/README.md`, "CI"). After pushing, wait for the summary check with `gh pr checks <n> --watch` (job `CI OK`) and fix failures from the CI logs (`gh run view <id> --log-failed`).
- **Nothing system-level on the Mac without asking:** never install or uninstall software (brew, npm -g), create VMs or Docker containers/images, use `sudo`, or change system settings automatically. Propose the command and let the user run it (`! <command>`). Scripts that change the host (`scripts/ci-acceptance.sh`, `scripts/ci-installer.sh`, the installer itself) are for CI runners and the test VM only.
- **Test VM:** `claude@192.168.1.117` is an internal Ubuntu 26.04 VM for manual testing (passwordless sudo, outbound internet only). Unlike the Mac, Claude may install and change anything there. `make deploy-testvm [REF=<pushed branch, tag or sha>]` builds that ref on the VM from GitHub and deploys it through the installer (`install` first, `update --force` afterwards); the UI is at `https://panel.192-168-1-117.sslip.io/` (Caddy `tls internal`). Details in `docs/dev/README.md` ("Test VM").
- **Git and GitHub:** the repo is `Bernotese/mc-panel`; use `gh`. Never commit to or push `main`. Every change goes on a branch (`feat/…`, `fix/…`, `docs/…`, `chore/…`) and into a PR whose CI must be green. Merging PRs, deleting remote branches and pushing tags (a `v*` tag publishes a GitHub release) only after the user says so.
- **Implementation with agent teams:** plan tasks (`docs/superpowers/plans/`; a sub-project's plans are deleted once it is merged, its spec stays) are implemented by Claude Code agent teams (enabled in `.claude/settings.json`). The lead splits the work into tasks with disjoint file sets and integrates; teammates load this file but not the lead's conversation, so each spawn prompt names the plan file, the task numbers and the branch. Each teammate works in its own git worktree on its own branch (`git worktree add ../mc-panel-wt/<branch> -b <branch> origin/main`), runs `make check` and `make test-vm` before reporting a task done, and never edits files assigned to another teammate. Keep teams small (3–5 teammates) and shut teammates down when their work is merged.

## Architecture

There are three binaries, built from `cmd/panel`, `cmd/agent` and `cmd/files`, and they are separated by privilege:

- **panel** runs unprivileged as user `mcpanel`. It serves the web app and `/api`, and in production it listens on a Unix socket behind Caddy. It owns the SQLite DB (`modernc.org/sqlite`, no CGO). It also provides the CLI subcommands `serve`, `version`, `admin create`, `admin unlock` and `audit verify`.
- **agent** runs as root and exposes a narrow JSON API over a Unix socket (`internal/agent`). It accepts connections only from the configured panel UID, checked via peer credentials. It validates every request strictly, rejecting unknown fields, and checks ban prefixes in `agentapi`. It manages the nftables sets `mcpanel_jail4`/`mcpanel_jail6` and the container egress filter (chain `forward`, sets `mcpanel_egress_deny4/6`, `container_egress_deny` in `agent.toml`) in table `inet mcpanel` and is the only Docker client: Minecraft servers are containers built from a fixed, hardened template (`internal/agent/instances`), validated with `internal/agent/instancespec` (shared with the panel), and routed by hostname through the `mcpanel-router` container (mc-router, reloaded via SIGHUP). For the console it streams container logs (Docker `logs?follow`, sent to the panel as NDJSON), runs `rcon-cli` in the container via Docker exec (argv, no shell) and reads an instance's player list files through `os.Root` with `O_NOFOLLOW|O_NONBLOCK` (regular files ≤ 1 MiB only): the data directory is controlled by the container, so the root agent never follows a path out of it. In dev mode Docker is off unless `MCPANEL_DEV_DOCKER=1`. The design goal is that a compromised panel does not give root on the host. If the agent fails, the panel reports `503 agent_unavailable`; in-app jails still apply.
- **files** runs as `mcpanel-mc` (the Minecraft containers' user) with no capabilities and `no_new_privs`, never as root (it refuses to start as root). It serves the file browser over its own Unix socket (`internal/files`; contract and path rules in `internal/files/filesapi`, shared with the panel) and accepts only the panel UID and root (like the agent); in production systemd creates the socket (`mcpanel-files.socket`, group `mcpanel`, 0660) and hands it over via `LISTEN_FDS`, so the service needs no supplementary groups. Every request opens `<instances_dir>/instances/<id>` with `os.Root`; symlinks are never followed (`Lstat` before, `Stat` + `os.SameFile` after opening), `.rcon-cli.*` and `.mcpanel-*` are hidden (case-insensitive), `rcon.password` in `server.properties` is redacted on read, download and folder zip (and kept on write). Uploads and downloads are streams, zip extraction is a job (pre-checked central directory, temp dir, re-counted sizes; one job per instance). `POST /v1/jars` lists the top-level `.jar`/`.jar.disabled` files of `plugins/` or `mods/` with sha256/sha512 (cached by device/inode, size, mtime and ctime) and best-effort metadata from `plugin.yml`/`paper-plugin.yml`/`fabric.mod.json`/`neoforge.mods.toml`; `PUT /v1/upload` takes an optional `sha256` or `sha512` and compares before `fsync`/`rename` (`400 hash_mismatch`, nothing left behind). Writes that grow data (uploads, extracts, restores, backups, larger editor saves) need free space above a reserve (the larger of `reserve_bytes` and `reserve_percent` in `files.toml`, otherwise `507 insufficient_storage`); reading, deleting and shrinking always work. It also runs backups (`/v1/backups/*`) with restic as a child process (`restic_binary`, empty environment, `--no-cache`) that never opens a path in a data directory: a backup is a tar stream the service writes from its `os.Root` walk (no symlinks or special files, hidden entries skipped, `rcon.password` redacted) into `restic backup --stdin`, ending with a `.mcpanel-end` entry (entry and byte counts) without which restore and download refuse the snapshot; restore and download read `restic dump` as a tar stream (restore: extracted with the zip rules into a temp dir, then the visible top-level entries are swapped by `rename`, journaled in `backups/restore-journal/<id>` so that the next start rolls an interrupted swap back or forward, and a swap that cannot be undone stays `stuck` and blocks further restores of that server until an operator resolves it; download: converted to a zip on the fly). One repo per server in `<instances_dir>/backups/repos/<id>` with its key in `backups/keys/<id>` (`backups/` is `mcpanel-mc` 0700, created by the agent); snapshot kind, pin and note are restic tags. One job per instance across extract/backup/restore/forget; without restic `/v1/backups/status` reports `available: false` and the other backup endpoints except purge answer `503 unavailable`. The service has no network access. The root agent never touches user-supplied file paths or archives.

The installer (`scripts/install/*.sh`, assembled into `build/install.sh` by `make installer`, released with every version) is the single source of truth for users, permissions, config files (`deploy/config/`), systemd units (`deploy/systemd/`, sandboxed; every directive is checked against what the service does), Caddy (from its official repository with a pinned key; the site and a `caddy.service` drop-in in `deploy/caddy/`, one marked import line in the Caddyfile, admin API on `/run/caddy/admin.sock` when the installer owns the Caddyfile) and the host firewall (table `inet mcpanel_fw` from `deploy/nftables/`, separate from the agent's `inet mcpanel`); change units and config there, not in `scripts/testvm-deploy.sh`. The panel takes its socket from systemd (`mcpanel-panel.socket`, `/run/mc-panel-web/panel.sock`, group `caddy`), like the files service. `update` backs up binaries, units, config and DB to `/var/lib/mc-panel-rollback/` and rolls back on a failed health check (exit 3; 4 if that fails too); after a healthy swap it also updates Caddy, its site and unattended-upgrades (failures there only warn). Step functions carry a per-file prefix and call system commands only through the `sys_*` wrappers of `lib.sh` (dry-run in tests).

Linux-specific code sits behind interfaces and is chosen with build tags (`_linux.go` / `_other.go` / `_darwin.go`). On macOS the firewall is a no-op that only logs, and peer credentials use `LOCAL_PEERCRED`.

### Request path and routing

`cmd/panel/app.go` (`buildApp`) is the only place that wires the packages together. Each feature package (`auth`, `defense`, `notify`, `users`, `servers`, `console`, `serverfiles`, `plugins`, `backups`, `monitoring`, `audit/auditapi`) has a `Handler` with a `Routes(api *rbac.Router)` method.

- Register routes only through `*rbac.Router`, with paths relative to `/api`, and give every route a `Rule`: `rbac.Public()`, `Authenticated()`, `Admin()` or `Server(perm, "param")`, optionally with `.WithSudo()`. Registering a route without a rule panics, and `TestEveryRouteDeclaresARule` catches any route added to chi directly. Feature code never calls `Route()`; it is used once, for `/api`.
- `cmd/panel/openapi_test.go` requires the registered routes to match the operations in `api/openapi.yaml` exactly. It also requires the `httpx` `Code*` error constants to match the contract's error enum. A new endpoint therefore needs a handler, an OpenAPI entry, regenerated TS types and an MSW mock handler (`web/src/mocks/handlers.test.ts` checks that every operation has a mock).
- Errors are always `{"error":"<code>","message":"..."}`, written via `httpx.WriteError`, with codes only from `internal/httpx/errors.go`. JSON is `snake_case` and IDs are int64.
- Everything outside `/api` goes to the embedded SPA (`internal/webui`, `go:embed` of `internal/webui/dist`, which the Vite build fills).

### Data

- There is one goose migration set in `internal/store/migrations`. Migrations run at startup, and the panel refuses to start if one fails.
- sqlc queries are split by domain in `internal/store/queries/*.sql`, and each generates its own `internal/store/<name>.sql.go` (`emit_interface: false`). Query names carry a domain prefix (`Auth…`, `Defense…`, `Rbac…`, `Audit…`, `Servers…`, `Plugins…`, `Backups…`, `Monitoring…`).
- Timestamps are `INTEGER` Unix milliseconds (`*_at` columns); convert with `time.UnixMilli` / `t.UnixMilli()`.
- The audit log is append-only and hash-chained: `hash = SHA-256(prev_hash || canonical JSON)`, written serially in a transaction. The API never updates or deletes audit entries.
- Tests use `storetest.Open(t)`, which returns a migrated temporary SQLite file, plus fixtures such as `storetest.CreateUser`.

### Minecraft instances

- The panel stores the desired state per server (`instances` table: type, version, java, memory, allowlisted properties, `desired_state`, `revision`) and `internal/servers` reconciles it with the agent every 10 s and after each user action. Spec changes bump `revision`; a running container with an older `mcpanel.revision` label shows "restart required". `memory_mib` is capped per host by `servers.MaxMemoryMiB` (`internal/servers/memory.go`, the only place of the formula: (MemTotal − 1 GiB) / 1.25, MemTotal from `internal/hostinfo`); `GET /servers/memory` gives the form its limits and recommendations.
- Server name = subdomain (`<name>.<base_domain>`, base domain in `instance_settings`). Container `mcpanel-mc-<id>`, data in `<instances_dir>/instances/<id>`.
- Only `instancespec.Env` decides container environment variables; never add itzg variables elsewhere.
- Version catalogs (`internal/servers/catalog`) and the plugin upstreams (`internal/plugins/upstream`) fetch fixed upstream URLs with a contact User-Agent and in-memory caches.
- Ops, whitelist and bans belong to the server itself (`ops.json`, `whitelist.json`, `banned-players.json` in its data directory): the panel never sets `OPS`/`WHITELIST`; the Players tab reads the files through the agent and changes them through RCON. `whitelist_enabled` stays an instance property.
- `internal/console` serves the live log as Server-Sent Events (`/servers/{id}/console/stream`: per-write deadlines via `http.ResponseController` instead of the server's `WriteTimeout`, reconnects to the agent across container restarts, re-checks session and permission every 5 s) and console commands and player actions as normal POST requests (CSRF, 30/min per user, audited as `server.console_command`/`server.player_action`). Player actions map an enum to fixed RCON commands; user text never becomes a command. `server.view` sees online players, `server.console` everything else.
- `internal/serverfiles` exposes `/servers/{id}/files/*` (`server.files`, which means full trust: uploading a plugin runs code in the container). `POST …/files/upload` and `PUT …/files/content` are exempt from the 1 MiB body limit; upload and download run with per-operation deadlines instead of the server timeouts (no buffering, 2 uploads per user); writes, uploads, renames, deletes, extracts and downloads are audited as `file.*`. Extracting needs a stopped server (agent state); while an extract job runs, power start/restart answer `409` and the reconcile loop does not start the server.
- `internal/plugins` exposes `/servers/{id}/plugins/*` (`server.plugins`, full trust) for paper/purpur (plugins from Modrinth and Hangar, `plugins/`) and fabric/neoforge (mods from Modrinth, `mods/`); other types answer `409 plugins_unsupported`. `internal/plugins/upstream` talks to fixed bases (`api.modrinth.com`, `hangar.papermc.io`) and downloads jars and icons only from `cdn.modrinth.com`/`hangarcdn.papermc.io` (https, redirects only there). The panel streams each jar to the files service with the upstream checksum (`UploadChecked`); it never writes plugin files itself. The disk is the source of truth; `plugin_installs` only remembers the origin of panel-installed jars (filename + sha512), other jars are matched via Modrinth `version_files` or shown as manual. Install/update run as in-memory jobs (one per server, four per panel, dependencies first); icons go through the proxy `/servers/{id}/plugins/icon` (CSP unchanged). Installs, updates, toggles and removals are audited as `plugin.*`, one entry per jar. The mrpack import (`/servers/{id}/plugins/mrpack/{preview,import}`, fabric/neoforge only) takes only the pack's `modrinth.index.json` (the browser extracts it), matches every `mods/*.jar` by sha512 on Modrinth and installs through the same job (`kind: mrpack`); it never downloads from URLs in the pack.
- `internal/backups` exposes `/servers/{id}/backups/*` (`server.backups`: reads every file via the download and can roll the server back; restore and snapshot delete need sudo). restic is the source of truth for snapshots; `backup_schedules` holds schedule (`off|interval|daily|weekly`, time zone `instance_settings.backup_timezone`), retention (`keep_*`, applied with `restic forget` to scheduled snapshots only, `pinned` kept), the last scheduled run and `saveoff_since`. A minute ticker (`clock.Clock`) queues due runs; one backup/restore/delete job runs panel-wide (FIFO, one per server, `409 backup_running`). A running server is backed up between RCON `save-off`/`save-all flush` and `save-on`; `save-on` follows on every path, and after a crash the panel sends it at start (`saveoff_since`). A restore holds the data gate (`servers.DataGate`, shared with extract: no start, no reconcile start), stops the server, takes a `pre-restore` snapshot, restores, and lets the reconcile loop start it again. Failed scheduled backups and restores notify `backup.failed` (once per 6 h per server); user actions are audited as `backup.*`; `DELETE /servers/{id}?purge_backups=1` removes the repo.
- `internal/monitoring` samples every 30 s (agent status; Server List Ping through mc-router at `monitoring_ping_addr` with the server's FQDN, bounded and never through the root agent; TPS/MSPT via RCON once a minute, every 5 s only for 30 s after a `metrics/live` call; host values from `/proc` and `statfs(instances_dir)`), stores raw/5-min/1-h series in SQLite (`metrics_raw` 24 h, `metrics_5m` 7 d, `metrics_1h` 30 d; missing values are gaps, never 0), evaluates `server.down`/`server.recovered`, `server.crash_loop` and `host.disk_low`/`host.disk_ok` with persistent state (`alert_state`; 5 min grace after every start, data gate, per-server `down_alerts`, disk hysteresis, reminder every 24 h) and sends them through `notify`. The agent only adds `restart_count`. Settings changes need sudo and are audited (`monitoring.settings_update`, `server.alerts_update`). Charts are own SVG components (no chart library).
- Docker integration and the instance acceptance (`scripts/ci-instances.sh <shard>`: five parallel shards in `scripts/ci-instances/`, the panel built with `-tags acceptance` and `MCPANEL_ACCEPTANCE_TIMESCALE=10` so monitoring and the backup tick run ten times faster (`internal/timescale`, factor 1 in every other build), including the console endpoints, the files service, plugin installs from the real Modrinth and Hangar, backup/restore/download with a real restic and monitoring with alerts (pings dropped by an nftables rule, delivery checked against an ntfy notifier at `https://ntfy.invalid` in the panel log) through the panel in production mode) run only in CI.

### Frontend (`web/`)

React + TypeScript + Vite, TanStack Router (file-based in `src/routes`) and Query, Tailwind and shadcn/ui (`src/components/ui`), react-i18next with `de` as the default and `en`. API types are generated from the OpenAPI spec, and the fetch wrapper in `src/api` sends the CSRF token (`X-CSRF-Token`) automatically. A global sudo dialog handles `sudo_required` and retries the action. No inline scripts or external CDNs are allowed (CSP). `npm run build` refuses to build with MSW active. The console reads the log with `EventSource` and renders it with `@tanstack/react-virtual`; ANSI and `§` colour codes become spans, never HTML.

- **Design system (sub-project 7):** dark „M2“ and light „Clean“ are equal; all colours are hex tokens in `src/index.css` (shadcn names plus `--bevel-*`, `--slot-*`, `--status-*`, `--console-*`, `--mc-0…f`), and `src/styles/tokens.test.ts` checks their AA contrast in both modes — every new colour needs a value in `:root` and `.dark`. Utilities: `bevel`/`bevel-primary`/`bevel-danger`/`bevel-pressed`, `bevel-inset` (slots, inputs), `glow`, `pixel-heading`, `console-scope` (always-dark console with its own § colours), `pixel-pattern`. Fonts are self-hosted via fontsource: Space Grotesk (UI), Silkscreen (`font-heading`, only headings/labels/badges, ≥ 12 px), Pixelify Sans (`font-pixel`, MOTD and player names; stat values use Space Grotesk with `tabular-nums` for readability), JetBrains Mono. Shared blocks in `src/components/`: `PageHeader`, `Section` (instead of ad-hoc cards), `StatSlot` (missing values show „–“, never 0), `PingBars`, `PixelIcon`, `McText`. shadcn components keep their APIs.
- **Navigation:** icon rail (expandable with labels on desktop, `localStorage` `mcpanel.rail`) plus server tree (`features/layout`, collapsed state in `localStorage` `mcpanel.tree`; flyout on tablet, drawer on mobile). All pages share one content area (`mx-auto max-w-7xl` in `AppLayout`); long forms use two columns on wide screens. Server areas are routes under the layout route `routes/_app/servers/$id` (index = overview, `monitoring`, `console`, `players`, `files`, `plugins`, `backups`, `settings`); `serverSections(server, isAdmin)` in `features/servers/sections.ts` alone decides which areas exist (tree, guards, breadcrumb), and `SectionGuard` redirects disallowed ones to the overview. The server header (status, address, power, stat slots) sits above every area; deleting a server is the danger zone at the end of its settings. The files area guards unsaved edits and running uploads itself (`useBlocker`).
- **Screenshots:** `make test-vm SUITE=shots` runs `web/e2e/shots/*.shots.ts` (helpers `shoot`/`signInMock`) against the mock in dark/light and desktop/mobile and copies the PNGs to `web/screenshots/` (gitignored); use it to review UI changes, it is not part of CI. Section components are tested through `src/test/render-section.tsx`.

## Conventions

- All time-dependent logic uses `clock.Clock` (`internal/clock`), never `time.Now()` directly, so tests can use a fake clock.
- Go tests use only the standard library (no testify etc.).
- Requests and DB calls always take a context (`NewRequestWithContext`, `QueryContext`/`ExecContext`).
- Lint exceptions go into `.golangci.yml` as a targeted rule (path, linter and text, with a reason) or into `//nolint:<linter> // <reason>` on the line. Never disable a linter globally. The `common-false-positives` preset is deliberately off, so gosec G103/G204/G304 need a justification each time.
- Imports are formatted with gofmt + goimports, with local prefix `github.com/Bernotese/mc-panel` (`golangci-lint fmt ./...`).
- The string `mcpanel` (nftables table and sets, system users `mcpanel`/`mcpanel-mc`, Docker names `mcpanel-mc-<id>`/`mcpanel-router`/networks `mcpanel-mc` and `mcpanel-net-<id>`, labels `mcpanel.*`, `mcpanel.theme` localStorage key) is a runtime name, not the module path. Do not rename it.
- Commits use Conventional Commits.
